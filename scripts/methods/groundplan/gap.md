# GroundPlan Implementation Gaps

This file records implementation gaps and design-to-code choices for the current
GroundPlan adapter.

## Current Gaps

1. The main Grounder is deterministic Python, not Gemini function calling.
   `grounding/gemini_grounding_prompt.md` is kept as a future experiment, but
   the current code follows the design principle that grounding should execute
   a validated restricted API program through a restricted map API without
   reinterpreting language.

2. GroundPlan is now API-program-only: `--parse-mode api` is the default and
   only supported parser mode. The LLM emits a restricted Python-like API
   program, which is AST-validated and compiled into `GPProgramSpec`.

3. `where(...)` predicate grounding is implemented for the current prompt-facing
   subset: `count(...)` comparisons, `count_next_to(...)`, `count_near(...)`,
   `contains(...)`, `near_to`, `far_from`, `next_to`, `on_top_of`, `in_corner`,
   `between`, and call-style Boolean `and/or/not`. This is still not a full
   typed predicate language; relation thresholds are fixed deterministic
   heuristics, and arbitrary nested grammar forms beyond the supported
   call/comparison subset should be added alongside explicit Grounder semantics.

4. Geodesic ranking currently uses the same center-distance approximation as
   Euclidean ranking. Full implementation should compute traversable-map
   distances without exposing paths or coordinates outside the Grounding API.

5. Planner supports the design's initial segment-level mechanisms: target goal
   regions, forbidden regions, ordered required regions, near/far/relative soft
   costs, clearance, and heading smoothness. It defers exact circling, S-shaped
   paths, U-shaped paths, exact retracing, and arbitrary path drawing automata.

6. Passage-region construction is boundary-derived from adjacent room labels.
   It does not yet use door/doorframe semantic entities to refine passage
   regions.

7. Planner weights are fixed constants in `config.py`. They are not generated by
   the LLM. Clearance has been manually strengthened after planner-only tests
   showed wall-hugging behavior, but the full weight set has not yet been tuned
   against a validation set.

8. Object goal regions follow the 0.3m footprint-dilation rule from the design.
   If a target region is empty or blocked by hard constraints, the planner
   returns a failure instead of choosing an arbitrary fallback endpoint.

9. The current implementation saves intermediate JSON per episode as
    `<prediction>.steps.json`. It does not yet provide aggregate parser,
    grounding, or planner diagnostic summaries across a full run.

10. Typed IR records live in `ir.py` rather than `types.py`. Directly executing
    `scripts/methods/groundplan/run.py` puts this directory on `sys.path`, and a
    local `types.py` shadows Python's standard-library `types` module.

11. The runner now supports a bounded LLM repair loop after deterministic
    grounding failures. This is a practical addition requested during debugging:
    the repair prompt sees the original instruction, previous API program,
    grounding error, and category counts, then rewrites the API program once by
    default. This departs from the pure one-pass Parser
    -> Grounder flow in `design.md`, but preserves the restriction that no
    object IDs, coordinates, paths, evaluator feedback, or metric details are
    exposed to the LLM.

12. `planner/debug_annotation_planner.py` is an oracle diagnostic runner. It
    intentionally uses benchmark annotation fields, including hard constraints,
    must-avoid regions, soft reference objects, and near-object anchors, to
    isolate the planner. Annotated `path_shape_preference` constraints are
    currently recorded as skipped instead of being converted from GT reference
    trajectories. These GT fields are not available to the normal GroundPlan
    inference path.

13. Weight tuning alone did not improve `path_shape_preference` scores in the
    planner-only debug runner. The active planner cost channels cover
    near/far/relative preferences, clearance, and path length; after removing
    GT reference-trajectory anchors, there is no remaining cost term that
    encodes circling, wall-following, partial loops, S-shapes, or retracing.
    Reaching high path-shape nDTW without GT trajectories requires implementing
    the design's path-shape machinery, such as `circle(...)` lowered to ordered
    boundary/around-object regions or an event-state automaton.

15. The main Grounder now supports an approximate `circle(reference, fraction,
    direction)` DSL expression by lowering it into ordered hard waypoint regions.
    Object circles are clipped to the object's room; room circles sample
    traversable waypoints near the room boundary. This is a benchmark-native
    approximation for explicit circle/loop instructions, but it is not a full
    path-shape automaton and does not yet cover exact S-shapes, retracing, or
    arbitrary wall-following.
